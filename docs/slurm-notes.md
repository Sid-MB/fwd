# Slurm backend notes

How `fwd` maps its concepts onto a Slurm cluster, why the layout is what it is, and what the other layers
(`ops/launch.py`, `bootstrap.sh`) must do to cooperate with it.

Code: `src/fwd/backends/slurm.py` (protocol implementation, ssh-touching) and `src/fwd/backends/slurm_job.py`
(pure `job.sh` rendering). Tests: `tests/test_slurm.py` — fully offline, no cluster needed.

## Concept mapping

| fwd concept | Slurm reality |
| --- | --- |
| target machine | the **login node**, pinned to a concrete host on first connect |
| `remote_dir` | `<remote_base>/<project_name>` on shared scratch |
| `tool_prefix` | `cfg.tool_prefix` or `<remote_base>/.fwd-tools` |
| `scratch` (caches) | `<remote_base>/.fwd-cache`, exported to bootstrap as `FWD_SCRATCH` |
| session process | detached tmux session `fwd-<name>` **on the login node** |
| the compute job | `salloc ... srun --pty bash -lc '<payload>'`, started by that tmux session |
| session id | Slurm job id, found via `squeue` by job name `fwd-<name>` |
| `fwd stop` | `scancel` + `tmux kill-session` |
| `fwd rm` | stop + `rm -rf <remote_dir>` (guarded to `remote_base`) |

## Why tmux runs on the login node

`salloc ... srun --pty` is an *interactive* allocation: the process that runs it owns the job's lifetime. If ssh owned
it, closing the laptop would cancel the job. So the launch is:

```
ssh login-node → tmux new -d -s fwd-<name> 'bash <remote_dir>/.fwd/job.sh'
                                  └── job.sh: source fwd-env.sh; exec salloc ... srun --pty bash -lc '<payload>'
```

The tmux pane's only process is `salloc` (note the `exec`), so `scancel` collapses the pane and killing the tmux
session releases the allocation — no orphaned wrapper shell either way.

Everything else — rsync, `bootstrap.sh`, dependency installs, Claude state upload — also runs on the **login node**:
compute nodes usually have no outbound internet, and the filesystem is shared with them anyway, so anything installed
from the login node is visible inside the job.

## Login-node pinning

`login_host` is almost always a round-robin alias (`login.hpc.example` → `login1..login4`). A tmux session only exists
on the machine that created it, so a later `fwd attach` landing on a different node would report "no session".

`provision()` therefore runs `hostname -f` on first connect and records:

- `backend_ids["login_host"]` — the concrete node, used to build every later endpoint
- `backend_ids["login_alias"]` — what the config said
- `backend_ids["pin"]` — `"hostname"` (pinned to a real node) or `"alias"` (fallback)

Some clusters do not publish per-node DNS externally. If the pinned name is not reachable, the backend falls back to
the alias, sets `pin = "alias"` and returns a note — attach may then land on the wrong node, which the user should
know about. `proxy_jump`, `key_path`, `port` and `user` always come from current config, so pinning changes *which*
node we land on, never *how* we get to the cluster.

## Generated `job.sh`

Written to `<remote_dir>/.fwd/job.sh` on every launch (so it is readable, tweakable, and removed by `fwd rm`):

```bash
#!/bin/bash
# Generated by fwd -- do not edit; regenerated on every launch.
set -euo pipefail

# Cache/venv redirections written by bootstrap.sh; Slurm propagates them into the allocation.
if [ -f /scratch/sid/fwd/.fwd-tools/fwd-env.sh ]; then
  . /scratch/sid/fwd/.fwd-tools/fwd-env.sh
fi

exec salloc --time=04:00:00 --cpus-per-task=4 -J fwd-demo --partition=gpu srun --pty bash -lc 'if [ -f /scratch/sid/fwd/.fwd-tools/fwd-env.sh ]; then . /scratch/sid/fwd/.fwd-tools/fwd-env.sh; fi; module load cuda/12.4 && module load python/3.12; cd /scratch/sid/fwd/demo; claude --resume abc123'
```

Rules baked into the renderer:

- `alloc` is parsed with shell rules (`shlex.split`) and re-joined, so quoted values survive.
- `--gpu X` appends `--gres=gpu:X` (numeric) or `--gres=gpu:X:1` (type) **only if** `alloc` does not already ask for
  GPUs — a config that requests GPUs always wins.
- `partition` / `account` become `--partition=` / `--account=` and are omitted when unset.
- `env_setup` lines are joined with `&&` so a failed `module load` aborts before `claude` starts on a broken
  toolchain. The top-level payload statements are joined with `;` because sourcing `fwd-env.sh` is best-effort.
- The whole payload is quoted **once**, as a single argv element for `bash -lc`, so a `claude_cmd` containing double
  quotes, single quotes or `$` reaches the compute node byte-for-byte. `tests/test_slurm.py` verifies this by running
  the generated script against a stub `salloc` that dumps its real argv.
- `fwd-env.sh` is sourced twice: on the login node (Slurm propagates the environment into the allocation) and again
  inside the payload (for clusters configured with `--export=NONE`).

## What `ops/launch.py` must do

Slurm is the only backend where tmux does not run `claude` directly. After the usual provision → sync → bootstrap →
deps sequence against `TargetInfo.endpoint` (the login node), the launch does:

```python
tmux_cmd = backend.claude_launch_wrapper(endpoint, session_name, remote_dir, claude_cmd)
remote.tmux_new(endpoint, f"fwd-{session_name}", remote_dir, tmux_cmd)
job_id = backend.find_job_id(endpoint, session_name)   # may be None while the job is still queueing
if job_id:
    session.backend_ids["job_id"] = job_id
```

Public surface (all documented in the module):

| method | purpose |
| --- | --- |
| `claude_launch_wrapper(endpoint, session_name, remote_dir, claude_cmd, *, tool_prefix=None, gpu=None)` | writes `job.sh`, returns the command for `tmux_new`. **The one call the launch path needs.** |
| `job_script(session_name, remote_dir, claude_cmd, *, tool_prefix=None, gpu=None)` | pure render, for `--dry-run` / debugging |
| `write_job_script(endpoint, ...)` | plants `job.sh`, returns its absolute path |
| `find_job_id(endpoint, session_name)` | newest job id named `fwd-<session>`, or `None` |

`gpu` defaults to whatever `provision()` was given on the same backend instance, so a same-process launch does not have
to thread it through. A later relaunch in a new process should pass `gpu=` explicitly if the user used `--gpu`
(it is stored in `SessionState.flags`).

## Status and reattach-after-job-death

`status(session)` checks two levels:

1. login node unreachable → `GONE` (the state entry is useless)
2. `squeue -j <job_id> -h -o %T` → `RUNNING`/`COMPLETING` → `RUNNING`; `PENDING`/`CONFIGURING`/`SUSPENDED` →
   `PENDING`; terminal states, empty output, or a nonzero exit ("Invalid job id specified") → `JOB_ENDED`. A state
   squeue lists but fwd does not recognise maps to `RUNNING`: squeue only forgets a job after `MinJobAge`, so a listed
   job is by definition not gone. Both long (`%T`) and compact (`%t`, `PD`/`R`/`CG`) spellings are accepted.

If no `job_id` was ever recorded, the backend rescans by name once and otherwise reports `RUNNING` — the login node is
up and there is nothing to relaunch yet.

**Contract for `ops/attach.py`:** when `status(session) == JOB_ENDED`, do *not* attach to the stale pane and do *not*
error. Offer a relaunch:

```python
if backend.status(session) is TargetStatus.JOB_ENDED:
    if ui.confirm("Allocation for 'demo' has ended. Request a new one?", default=True):
        remote.tmux_kill(endpoint, session.tmux_session)
        tmux_cmd = backend.claude_launch_wrapper(endpoint, session.name, session.remote_dir, claude_cmd)
        remote.tmux_new(endpoint, session.tmux_session, session.remote_dir, tmux_cmd)
        session.backend_ids["job_id"] = backend.find_job_id(endpoint, session.name) or ""
```

The tmux session must be killed first: its pane holds a finished `salloc` and reusing it would attach the user to a
dead shell. Sync/bootstrap do not need to rerun — the shared filesystem still has everything.

`PENDING` is normal and can last hours on a busy cluster. Attach should say "queued" rather than fail; the tmux
session exists and shows `salloc: Pending job allocation N`, so attaching is actually useful.

## Path guard on `fwd rm`

`destroy()` refuses to `rm -rf` unless the recorded `remote_dir` is absolute, normalises to a path strictly inside the
currently configured `remote_base`, and is not `remote_base` itself. Hand-edited state, a config repointed at another
cluster, or a truncated path raise `ProvisionError` with the path to delete manually. Note that a `remote_base`
containing `$HOME`/`~` will fail the guard (we do not expand remotely before comparing) — use a literal path or
`/scratch/$USER`-style paths only if you accept manual cleanup.

## `fwd-env.sh` contract (what the Slurm backend needs from `bootstrap.sh`)

`bootstrap.sh` receives `FWD_TOOL_PREFIX`, `FWD_REMOTE_DIR` and `FWD_SCRATCH` and is expected to write
`$FWD_TOOL_PREFIX/fwd-env.sh`, a plain POSIX-sourceable file with no side effects beyond exports. `job.sh` sources it
on the login node and again inside the allocation, so it must be idempotent and must not print anything.

Required exports when `FWD_SCRATCH` is set (HPC home directories have inode quotas a single `node_modules` can
exhaust — this is the single most common Slurm failure mode):

| variable | value | why |
| --- | --- | --- |
| `PATH` | `$FWD_TOOL_PREFIX/bin` prepended | so `claude`, `uv`, `bun`, `node` resolve inside the allocation |
| `UV_CACHE_DIR` | `$FWD_SCRATCH/uv` | uv's wheel cache, tens of thousands of files |
| `UV_PROJECT_ENVIRONMENT` | `$FWD_SCRATCH/venvs/<project>` | keeps `.venv` off the (possibly small, possibly no-exec) project quota |
| `XDG_CACHE_HOME` | `$FWD_SCRATCH/xdg` | catches everything else that respects XDG, including `~/.cache/claude-cli` |
| `BUN_INSTALL_CACHE_DIR` | `$FWD_SCRATCH/bun` | bun global cache |
| `npm_config_cache` | `$FWD_SCRATCH/npm` | npm/npx cache |
| `TMPDIR` | `$FWD_SCRATCH/tmp` (only if unset by the cluster) | some clusters set a per-job `TMPDIR`; do not override it |

Nice to have: `FWD_TOOL_PREFIX` and `FWD_SCRATCH` re-exported, so a user in the pane can see what fwd chose.

If `FWD_SCRATCH` is unset (ssh/RunPod backends), the file should still exist and export `PATH` only.

## Config examples

Typical university cluster, GPU partition, external SSH host:

```toml
[targets.hpc]
backend = "slurm"
login_host = "login.hpc.example.edu"
user = "sid"
proxy_jump = "sid@external.example.edu"    # omit if the login node is publicly accessible
key_path = "~/.ssh/id_ed25519_hpc"
remote_base = "/scratch/sid/fwd"           # MUST be scratch, never $HOME
tool_prefix = "/scratch/sid/fwd/.fwd-tools"  # optional; this is the default
alloc = "--time=04:00:00 --cpus-per-task=8 --mem=32G"
partition = "gpu"
account = "cs-research"
env_setup = [
  "module purge",
  "module load cuda/12.4",
  "module load python/3.12",
]
```

Per-project override (`.fwd/config.toml`) that only changes the allocation:

```toml
[targets.hpc]
alloc = "--time=08:00:00 --cpus-per-task=16 --mem=64G --gres=gpu:a100:1"
```

CPU-only cluster with no partition/account and a direct login:

```toml
[targets.cluster]
backend = "slurm"
login_host = "cluster.example.org"
user = "sid"
remote_base = "/work/sid/fwd"
alloc = "--time=02:00:00 --cpus-per-task=4"
env_setup = ["module load gcc/13"]
```

## Testing without a cluster

`tests/test_slurm.py` uses a duck-typed `FakeEndpoint` recording `run()` calls and replaying canned `squeue`/`hostname`
output — every backend path (pinning, fallback, status table, stop/destroy guards, doctor) is covered offline. The
quoting tests execute the rendered `job.sh` locally with a stub `salloc` on `PATH` that dumps its argv, which is the
only way to be sure the four layers of shell interpretation cancel out.

Real-cluster smoke test, when one is available:

```
fwd doctor --target hpc          # ssh, squeue, tmux, remote_base writable, scratch space
fwd up --target hpc              # watch: pinned host in state.json, .fwd/job.sh on scratch, squeue shows fwd-<name>
fwd ls                           # PENDING while queued, RUNNING once allocated
fwd stop <name> && fwd ls        # JOB_ENDED
fwd attach <name>                # must offer a relaunch, not an error
fwd rm <name>                    # scratch project dir gone
```
